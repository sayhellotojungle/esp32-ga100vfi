# 解锁与 poison：判据、处置与已固化防护

适用范围：GA100 CMP 170HX 电压毛刺解锁与 FF 烧写。本文给出判据、处置顺序，以及每条判据在代码与脚本中的落地位置。命令值与寄存器定义见 [../README.md](../README.md) §2；FF 烧写规程以 ffcalc 仓库 `docs/BURNING.md` 为准。

---

## 一、VRM 锁状态：三种，处置不同

判据只有一个：`z` 打印的 `pwd`，即 `STATUS_CML(0x7E) & 0x08`。固件答复的文字不许用于判锁态。

| 状态 | 现象 | 成因 | 处置 |
|---|---|---|---|
| 无锁 | `pwd=1` | 正常 | 直接开火，不再发 `u` |
| 故障锁 | `pwd=0`，`z` 能读到 | 过压/欠压事件把故障闩上，控制器因此拒绝密码 | 先 `CLEAR_FAULTS(0x03)` 再交密码，一发即解，无需断电 |
| 总线无应答 | `z` 报 `ERR status read` | 接线/地址/供电/总线被占用 | 查硬件，与锁无关 |
| 真死 | 先清故障再交密码仍 `pwd=0` | 极少 | 拔 12V + 3V3 ≥30 s |

### 1.1 故障锁必须先清故障

`GA_CLR`（`0x03`）排在毛刺时间线内，时间线又被 `ensure_unlocked()` 挡在门外：

```
开火 → ensure_unlocked() → 密码被拒（故障闩着）→ 时间线不执行
     → GA_CLR 发不出去 → 故障永远闩着 → 下一发同样空转
```

固件解锁路径因此固定为先 `0x03` 再密码 `0xF2`（`main/main.c` 的 `unlock_state()`）。`0x03` 是普通命令，不受写保护门控；受保护写只有 `0x13/0x1F/0x21/0xE1` 一类。回归锁：`test/test_main.c` 的故障闩锁模型。

### 1.2 无锁时不发 `u`；开火前不发 `w`

`ensure_unlocked()` 除密码外还写 `0x13`（写保护）与 `0x46`（config-id）。预检规则：`pwd=1` 什么都不发，直接打。

裸打（`g`/campaign）之前不发 `w`：`w` 把 VRM 交回 PWM-VID，GPU 接管后 `VOUT_COMMAND` 被压制，窗口无法出现。

### 1.3 `0x46=0x1229` 属于解锁，不是可选项

完整解锁序列（与参考实现 `pico-ga100vfi/firmware/pwmvid.c:215-225` 一致）：

```
密码 0x7C25 → 0x13=0 → 0x46=0x1229（config-id）→ 回读必须等于 29 12
```

`0x1229` 的作用是阻止 GA100 devinit 重新锁上 VRM。缺它时第 1 发释放 `PEX_RST` 后 devinit 即把 VRM 重新锁死，其后每发都在解锁门口返回。`ensure_unlocked()` 现在写这三步并回读校验，写不进去即返回 `config-id-0x1229-refused`。

约束：**任何脚本不得手写 `0x46=0x1228`**（等于把 devinit 那把锁重新装上，实测立刻变成"密码真拒"）。`0x46` 与 fast/stock profile 表（BA/B9/30/31/32/45）无关，`profile_apply(false)` 不会把它写回。

### 1.4 空发的识别

`pwd=0` 时开火 = 每发都在门前 `return`，`GA_RST_LOW` 未执行，判决是对一张未被碰过的卡回 `under`。识别方法（任一）：

- 串口 `glitch done ... writes_failed=1`；
- 示波器/逻辑分析看 `PEX_RST` 是否真的下拉；
- `host/ga100vfi/cli.py` 只在 `writes_failed == 0` 时计入判决。

判决数为 0 的一轮不是参数问题，是没有打出去。两者的排查方向相反。

### 1.5 解锁错误报告分三类

`unlock_cmd()` 分报（`main/main.c`）：

| 输出 | 实际发生 | 处置 |
|---|---|---|
| `unlock ERR unreachable` | 总线不应答 | 查线/地址/占用 |
| `unlock ERR password-refused` | 密码被拒（含已先发 `CLEAR_FAULTS` 仍被拒） | 查故障位、`STATUS_CML` |
| `unlock PARTIAL pwd=1 0x46-failed` | 密码通过，config-id 写不进 | devinit 已锁，见 §1.3 |

规则：只能给一个字符串的错误报告不许用于硬件结论。

## 二、熔丝控制器：四态与恢复

```
脉冲过深（over）
  → 控制器进 poison：FUSECTRL = 0xBADFxxxx
  → 此后任何 BAR0 读取都可能挂死 PCIe 上游 → 整机复位（事故 logs/02）
  → 也可能设备层不再应答配置读：id=ffff:ffff bar0=0xffffffff（判 lost）
```

### 2.1 四态判据

`host/ga100vfi/classify.py` 的 `fusectrl_state()` 是唯一判据函数，判决链、CLI 战役循环、台架脚本共用：

| 读数 | 状态 | 判决 | 处置 |
|---|---|---|---|
| `0xE0040000` | `idle` | 可判决 | 放行 |
| `0xFFFFFFFF` | `unreachable` | `lost` | 一发 `lost` 即停战（代理 `--max-lost`，默认 1），不发补发 |
| `0xBADFxxxx` | `poisoned` | 不判决 | 抛 `Poisoned`，停战役，退出码 3/4 |
| 其他（实测 `0x00000000`） | `unknown` | 不判决 | 抛 `ControllerUnknown`，同上处置 |

两条硬性顺序与预算约束：

1. `unreachable` 必须先于 `poisoned` 判定：`0xFFFFFFFF` 的状态位同为 31；
2. 判定只允许一次 `FUSECTRL` 读。命中危险态后不许"再读一次确认"、不许 `classify`、不许 `capture`。

回归锁：`host/tests/test_regressions.py::PoisonGuard`，断言访问序列恰好等于 `[("r", FUSECTRL)]`。把 `STATE_UNKNOWN` 改为 `STATE_IDLE` 立刻 8 处 FAIL（已用变异验证）。

### 2.2 固化位置

| 层 | 位置 | 行为 |
|---|---|---|
| 判决链 | `host/ga100vfi/classify.py` `classify()` / `snapshot()` 第一行 | 抛 `FuseControllerStop` 子类，除这一读外不碰 BAR0 |
| HTTP 判决代理 | `host/ga100vfi_agent.py` `gpu_verdict()`（存在性探针之前）、`run_forever()` | 打印停火原因 → `stop_board()` → 退出码 3；每发判决带寄存器快照 |
| 串口战役 CLI | `host/ga100vfi/cli.py` `cmd_campaign` / `cmd_classify` / `cmd_baseline` | 停循环、输出 `poisoned_stop`、退出码 4 |
| 烧写 | `host/ga100vfi/burn.py` | `FuseError` |
| 台架 | `bench/poison_check.sh`、`bench/window.sh` 第 0 步、`bench/crack.sh` 第 1 道门 | 单寄存器一问 |

### 2.3 恢复顺序

1. **板子自己拉一次 `PEX_RST`**：控制台 `j`（按住）→ ≥2 s → `J`（释放），然后 `bench/poison_check.sh` 重问一次 `FUSECTRL`。2026-11-21 实测：真发打出的毒态（`g 358 -60 750 -20 0 1 0 3 198 150 117 0`，`wfail=0`）从 `0xbadf510e` 回到 `0xe0040000`，device id 同时从 `10de:2080` 回到 `10de:20c2`，全程不需要动电源、也不需要重启判决机；
2. 板子拉不动再重启判决机（POST 拉一次 `PERST#`，卡与控制器一起走 POR）；
3. `bench/card_probe.sh`：卡重新枚举 → `bench/poison_check.sh` 验 `FUSECTRL=0xE004…` → 继续；
4. 卡未回来（全盘无 `10de`）时，先让板子问一次 PMBus（`@r 25 7e 1`）判断卡有没有电；`bench/link_retrain.sh` 的"对桥发 Retrain + rescan"本卡**实测 4/4 无效**（桥 `LnkSta` 停在 `0x1081`、`dllLA` 始终 0，EP 侧不重试训练），只当排除桥侧故障的便宜判据，别指望它救卡；
5. 仍不回 → 拔 12V + 3V3 ≥30 s。判据为第 3、4 步的组合：有电、无链路、软件手段用尽，剩下的是 PHY 的 POR。

适用边界（更新）：本节原来写的是"poison 来自真发时第 1–3 步不足以恢复，需拔电"，那条已被上面那次实测推翻 —— 真发毒态同样吃 PERST#。仍保留最后一档断电兜底，因为掉链 + PHY 不起训练是另一件事（见本节末）。

**掉链（毛刺后 `config` 全 1）的两条实测事实**，2026-11-21：卡**从不自己回来**（零干预观察 60 s、240 次只读采样），只有 `PEX_RST` 按住 ≥2 s 再释放能救（~0.3 s 重新枚举）；而每发 `g` 的时间表本身就带一次 `PERST#`（`main/glitch_plan.c:153` 拉低、`:164` 释放）。两条合起来的后果：掉链的那一发只能靠"再重放一次熔丝链"救回来，判决作废 —— 掉链＝白烧一发，降它只能靠坐标与节奏，不能指望恢复手段。

`10de:2080` 这个 config 指纹是 2026-11-21 顺手量出来的：控制器一 trip，设备号就不再是 `20c2`。它是**一次 BAR0 都不开**就能看出"上一发把控制器打毒了没"的唯一信号，因此在红线 1 之下比 `FUSECTRL` 更便宜（`bench/poison_check.sh` 现在会主动点出它）。

Gen4 PHY 训练状态与控制器 poison 是两件事，处置不可互抄。

### 2.4 电压窗口实测（本卡，`3×222µs@334` / `delay=54` / `fast=1`）

| vd | PMBus 码 | FUSECTRL | DSOV | CRC | 结果 |
|---|---|---|---|---|---|
| 334 | 53（331 mV） | `e0040000` | 1 | `0x57` / `0x55` | under（太浅） |
| 330 | 53（同 334） | `e0040000` | `ffffffff` | — | lost（链路未起）→ 同轮第三发 poison |
| 309 | 49（250 mV 档） | `00000000` | 1 | `0x77` | `unknown` 态；同电压下一发 poison |
| **326** | **52（325 mV）** | `e0040000` | **0** | **`0x55`** | **goldilocks，第 1 发命中** |

两条规则：

1. `vd` 非线性。PMBus 码 = `(mv*16+50)/100`，LSB 6.25 mV：`vd=330` 与 `vd=334` 是同一个码 53，写入电压相同。换档必须跨过一个 LSB（334 → 326 → 319）。
2. 一发 `lost` 即停火。`lost` 之后控制器处于半死态，补一发实测得到 poison。`bench/crack.sh` 的状态轮询只保证"这一轮不再补发"，它 3 秒一轮，追不上板子：`ga100vfi_agent` 把判决交回去的那一刻，板子在同一次 `campaign_poll()` 里就推进到下一发。第二张卡实测三发 `lost`，每一轮 `tries` 都是 2 —— 一发有判决、另一发谁也没判过（当时 `--max-lost` 默认 3，代理自认还没到停手的量，压根没下停止命令）。所以停火命令必须在**交回判决之前**发出，阈值默认 1；板子的 `running && stop_requested` 检查在收判决的同一次轮询里就会把战役收尾。

### 2.4.1 第二张卡（同 SKU `10de:20c2`，同一波形）：档案坐标不迁移

`3 × 222µs`、`gap 150`、`td=-40 vr=750 tr=-20`、`fast=1` 全程未动；下表只动搜索轴。

| 轴 | 坐标 | 结果 |
|---|---|---|
| 电压 @ `delay=54` | 344（码 55） | under |
| | 340 / 339（码 54） | under ×2、poison ×1（混现＝边界在此） |
| | 334（码 53） | lost ×1、poison ×1 |
| | 326（码 52，第一张卡的命中点） | **lost ×3**（含一发干净电源周期 + 最浅时序） |
| 时序 @ 码 54（340） | 20 / 54 / 90 / 120 | poison / 混现 / under / under（105 为空发，见下） |

三条结论：

1. **命中坐标随卡漂移，同 SKU 也不许复用。** 第一张卡第 1 发命中的码 52，在这张卡上三发全 `lost`，其中一发是在干净电源周期、`delay=120`（最浅时序）下测的 —— 排除了"退化周期把它打坏了"这个解释。发数不再投给它。
2. **结果对 `delay` 单调**：越小越深（脉冲串越晚、与启动期熔丝采样窗重叠越多）。码 54 的转折被夹在 20（poison）与 90（under）之间，而档案锚点 54 正骑在转折上。同一坐标分裂成两种结果不是玄学：板载调度抖动 `slip_us` 实测 16..268 µs，与我们想走的步长同量级。
3. **由此两条纪律**：小于约 100 µs 的 `delay` 步长在这块板子上不构成可分辨坐标，别拿它当网格；一个 `(delay, vd)` 为了**收第二份统计**再打一发等于拿一个电源周期掷硬币 —— 同档样本够了就走。
   但**把它当"分布的瞄准点"反复打是另一回事，而且是正解**：`slip_us` 实测 16..268 µs，同一组参数每发的有效落点本来就在一条上百微秒宽的分布里飘。于是把瞄准点钉在**边界浅侧一步**（本例 `340@75`，边界夹在 54 与 90 之间），三种落点的代价天然不对称 —— 落浅仍是 `under`（不花钱，战役继续）、落进窗口就是 `goldilocks`、只有极少数落太深才 `poison`。反之把瞄准点钉在已知混现的坐标（`340@54` 实测 2 under / 2 poison）每发都是对半分，一个周期两三发就作废 —— 禁的是这个。

判决行缺失时先分清是谁的责任，别急着怪代理或怪参数：

| 板载计数 | 含义 | 处置 |
|---|---|---|
| `nack>0`、`timeouts=0` | 执行阶段 PMBus 未应答，板子自己重跑同一坐标（`campaign.c` 的 `ST_READY/retry`） | 空发，不算坐标样本；它已被重跑，人工补发只会多烧一发 |
| `timeouts>0` | 板子等判决等到 `MANUAL_TIMEOUT_US=120 s` 才放弃 | 代理侧问题（判决没交回去），查 `agent.log` 与 `--max-lost` |

poison 的两类来源（这张卡 10 发里 3 发）：

- **物理必然**：判决判据（今天只有主机侧 `host/ga100vfi/classify.py` 一份；0.4.1 之前 `main/oracle.c` 另有一份）里 `DSOV!=0 → under`、`DSOV==0 且 CRC==0x55 → goldilocks`，而 poison 是控制器被按在欠压里跨过了装载阶段 —— 它是 `over` 的极端形式，与 `over` 之间**没有可停靠的中间态**。贴着边界往深侧探，每一发都有接近对半的概率掉进去。所以纪律是：新坐标一律从浅侧起（`delay` 由大到小排），一个电源周期里最冒险的那发排最后；已确认混现的坐标不再打。
- **流程错误（已消除）**：同一个电源周期里 `lost` 之后不 POST 就连打，加上代理当时"交完判决才停火"多带的那一发 —— 第 1–3 轮因此把 4 发烧死在码 52/53 上，卡最后要靠断电才回来。现在一发 `lost` 即停（`--max-lost` 默认 1，停火先于交判决），且每周期只开一次战役。

### 2.4.2 「一个电源周期只买得到一发」是概率，不是规则

第 13、14 轮用两种办法把"谁杀了卡"这件事拆开，坐标钉死在安全档 `350@delay=120`（码 56），波形一字未动。两发都是 `writes_failed=0` 的真发。

| 轮 | 两发之间 host 做了什么 | 结果 |
|---|---|---|
| 13 | 什么都不做（无代理进程、零 BAR0 会话、零配置写） | 一发之后卡从总线消失 |
| 14 | 同上，且开火前先单跑一次 `w`（战役收尾那套 restore） | 一发之后 240 s 内卡一直在总线 |

四条结论：

1. **代理无罪。** 第 13 轮 host 侧一个 BAR0 会话都没开、一次配置写都没做，卡照样消失。此前怀疑的"代理每发判决前的 `restore()` 那两次 `pwrite`（BAR0 基址 `0x10` + COMMAND 的 MEM enable）"被自己的实验否证。
2. **板子的收尾动作无罪。** 控制台命令 `w` = `hardware_enter()`（unlock：`CLEAR_FAULTS` + 密码 + 关写保护 + `CONFIGID 0x1229`）+ `restore_locked()`（`0x1F=0x30`、`0x21=0x7E`、500 ms、`0xE1=0xC2EA`、profile OFF→ON）+ `hardware_leave()`，正是每场战役收尾跑的那一整套。在卡已经跑起来的时候单独执行它，90 s 内卡不动；`/api/log` 里 `revert vout=1 mode=1 vmin=1 profile=1` 证明它真被执行、四次写全部成功。
3. **杀卡是概率事件，且与深度无关。** 码 56 比任何观测到 fatal 的档都浅两个码，第 13 轮一发即杀、第 14 轮一发无恙。因此"15/15 全发生在物理第 2 发之后"那张表读不得因果：那些第 2 发从来是紧接第 1 发之后 +5..13 s 打的，**它同时混淆了"第二发"与"打完还没恢复透"** 两个变量，而第 14 轮证明间隔足够时单发可以活。
4. **毛刺会让卡瞬断约 0.3 s 再自己回来**（实测 `t=+0.07 s` 缺席、`+0.32 s` 回来）。所以单次 config 全 1 读数**不能**判死；判定必须连续两次确认（0.25 s 分辨率下）。代理侧因 `first_read_delay=2 s` 恰好躲过了这个坑，但这是运气不是设计。

由此得到两条台架纪律：

- **`max=1` 的战役不会自己早停**，会一直等到 `MANUAL_TIMEOUT_US=120 s` 才计 `timeouts` 收尾。想提前结束必须在**卡已经启动完成之后**发 `op=stop`。
  **在 `settle` 里就发 `stop` 会把卡打死**（第 15 轮实测：`settle` 中 3.47 s 发 stop → 3.89 s `restoring` → 4.11 s 卡从总线消失，`writes_failed=0` 的真发）。原因就在下一行。
- **收尾那套写（`restore_locked()` 里的 profile OFF→ON = 一次故意的掉电再上电）只能打在"已经启动完成"的卡上。** 同一个动作，第 14 轮发生在 `+128 s`（卡早已启动完）→ 卡活；第 15 轮发生在 `+3.9 s`（卡还在启动）→ 卡死。所以台架的等待不能是固定秒数，必须等"**卡连续在场足够久**"这个事件，再去碰 VRM。
- **观察者必须增量落盘**。等到窗口结束才写 CSV 的写法，中途读到的永远是空文件，"还在等"与"什么都没发生"分不开；而这份记录是我们为这一发付了代价换来的。

**可重复性已由第 16 轮确立（同一电源周期 4 发全部出判决、卡活到最后）**，条件是每发都遵守上面那条"启动完成才碰 VRM"。节奏是：开火 → 等"卡连续在场 ≥30 s"这个事件 → 才 `op=stop` 让板子收尾 → 再确认在场 → 才开一次 BAR0 会话取判决。四条判决 `350@120`、`340@90`、`340@75`、`340@60` 全是 `DSOV=0x1 CRC=0x55 → under`，逐发实打证据 `writes_failed=0`、`slip_us` 96..247。此前"一个电源周期约只买一发"的真正成因不是卡脆也不是代理读，而是**收尾写落在启动过程中**；纠正之后一发约 45 秒，比原来等 120 秒判决超时还快。

同一坐标重复打是档案 §2.4.1 明许的（`slip_us` 16..268 µs 与步长同量级，每发有效落点本就在上百微秒宽的分布里飘），钉住边界浅侧一步反复打，而不是在每个新坐标上各打一发。

**但收尾那套写不是唯一凶器。** 第 18 轮走控制台 `g` 手动路径（`main.c:445-448`，`revert=0` 照抄 `campaign.c:73`），全程**零次** `restore_locked()`，`340@30` 第 1 发 `under`（`writes_failed=0`、`seq=1`），第 2 发同坐标打出后卡消失（`seq=2`、`wfail=0`）。也就是说毛刺本身足以致命，尤其当第二发是站在第一发留下的状态上打的：`revert=0` 使 `GA_MODE` 停在强制导通，只有主机侧 `restore_locked()` 才把它写回去 —— 于是"要它干净就得跑那套会杀卡的收尾"成了死结。解开它的办法是让时间表自己在 `post+500µs` 写回 `GA_MODE`（`glitch_plan.c:176-180`，也是 `glitch_args_defaults` 的默认值 `revert=1`），这样两件事都不要主机参与。

**第 19 轮把这句话收回一半，并给出正解。** 同一张卡、同一个电源周期、同样走手动 `g` 路径、坐标同样钉在 `340@30`，**只把最后一个参数从 `revert=0` 改成 `revert=1`**：连打 5 发（`seq=1..5`）全部 `writes_failed=0`、全部出判决（全 `DSOV=0x1 CRC=0x55 → under`）、卡活到最后，一发约 10 秒。第 18 轮那个"第二发死亡"因此不是毛刺的固有致死率，而是**残留状态**：`revert=0` 让 `GA_MODE` 停在强制导通，第二发是踩着自己的上发残留打的。

于是每发之间的清洁工有两个候选，都不是主机侧掉电重写：

| 清洁工 | 谁写回 `GA_MODE` | 实测 |
|---|---|---|
| 战役 + 收尾 `restore_locked()` | host，profile OFF→ON | 能连打 4 发（第 16 轮），但第 15/17 轮各杀一次卡 —— 它只能打在"已启动完成"的卡上 |
| **时间表自己 `revert=1`（`post+500µs`）** | 板子，一个时间锚点写 | **第 19 轮 5/5 存活，每发 10 秒，零 host 写** |

结论：**逐发 `revert=1` 的手动 `g` 路径是当前正解**，战役那套收尾从此不需要在循环里出现。（`revert=1` 也正是 `glitch_args_defaults` 的默认值，战役路径里 `args->revert=0` 是为了把恢复交给收尾统一做 —— 见 `campaign.c:73`。）

**台架纪律（第三条，用一发换来的）**：

- **参数不许经过第二次 shell 解析，开火前必须预演命令文本。** 一次坐标用 `;` 分隔、经 `arm_hammer` 原样拼进远端命令行的传递，被远端 bash 当成命令分隔符吃掉，`delay` 字段变空，板子收到 `g 334 -40 750 -20 0 1 0 3 222 150  1`（12 字段）。板子**不拒绝**这种命令 —— `strtol` 静默顺延，实际打出 `delay=1`，比已知 poison 的 20 深得多，白烧一发还把卡打死，而 `/api/status` 里一切"正常"。现在的三道闸：坐标格式硬校验 `^[0-9]{3}:[0-9]{1,4}$`、`shlex.quote` 逐个转义、开火前把每条命令原样打印并断言恰好 13 个字段。

`/api/log` 里能读到 `glitch vd=…`、`diag sw=…`、`glitch done … slip=… reset_slip=…`、`revert vout=… profile=…` —— 逐发物理证据（`writes_failed`、`slip_us`、`reset_slip_us`）本来就拿得到，不必等固件把裸 `printf` 改成 `console_printf`。此前把它记成 0.3.1 待办是错的。仍缺的只有 DSOV/CRC 的**保持时间**：判决都在打完后 8~60 s 才读，从没验证过这些位是长期锁存还是会自动清 —— 这一条决定全部 `under` 判决的可信度。

1. **`DSOV` 只在这张卡上读，`under` 是"没碰翻比较器"，不是"读晚了"。** 判官只有主机 BAR0 一条路：板子走 SMBPBI 直读 `DSOV` 的 `@P` 命令在本卡上**四次全部无回显** —— 板子读不到这颗 GPU，所以一切判决只能等卡重新枚举后由主机读。0.4.1 就是按这条结论删除了板载判决（旧 `mode=0`）、`@P` 与 `@O`：一条从未答过的通路留着，只会让战役在"每一发都被它判成 `lost`"的状态下把坐标烧完。

### 2.4.5 `DSOV` 不是电压比较器，是**熔丝位** `OPT_DISABLE_SW_OVERRIDE`

`host/ga100vfi/burn.py:27` 写得很直白：

```python
DSOV_STATUS = 0x00820084        # OPT_DISABLE_SW_OVERRIDE
```

而 `host/ga100vfi/burn.py:206` 的闸门是 `if self.rd(DSOV_STATUS) != 0: raise FuseError("DSOV is not 0 after SENSE_CTRL: not a usable window")`。所以：

- 读 `1` = OTP 里"禁止软件改写"这一位**已被烧成 1**，软件改写被锁死，这个窗口是关的；
- 读 `0` = 该位是 0，软件可以改熔丝 —— 这才是能烧的那扇窗。

由此，旧 `main/oracle.c` 里的注释 `dsov stuck: dip too shallow`（下拉太浅）**是一个未经验证的假设，本卡 24 发数据把它否掉了**：我们不是在把电压压得更深去碰一个比较器阈值，而是在赌**启动期读这颗 OTP 的那一瞬被欠压打断**。`under` 的正确读法是"这一位还是 1"，不是"压得不够深"。`host/ga100vfi/cli.py:75` 的 `under: dsov=1 (dip too shallow)` 同样要按这条改正。（该注释随 0.4.1 的 SMBPBI 判决一并消失，`main/oracle.c` 现在只剩判决词表；结论本身留在这一段。）

这条替换解释了三件此前无法解释的事：

1. **"每张卡体质不同"有了物理来源。** 第 1 张卡在 `326` 第一发就 `goldilocks`，说明它这一位本来就是 `0`（出厂即开）；本卡读 `1`（锁死），所以同样的坐标打多少发都不会"顺带命中"。别卡坐标不迁移不是玄学，是 OTP 内容不同。
2. **`331.25 mV` 必死与暴露时长无关**（666 µs 与 222 µs 都死）：`first = td - delay = -40 - delay`，而 `RST_REL` 在 `t = 0` —— 第一个下拉**横跨复位释放**，卡是带着 331 mV 起跑的，根本跑不到读熔丝那一步。
3. **0.93 ms 与 0~8.6 ms 都没撞上，不矛盾**：`delay` 与 `gap` 只是把下拉摊在启动早期，而 OTP 读可能发生在启动完成后几十毫秒到几百毫秒。

所以正确的打法是：**让第一个下拉整个落在复位期内（无害），把后面的下拉放到卡真正跑起来之后** —— 取 `delay > pw`（例如 `delay=1000`，第一个下拉落在 `-1040..-818 µs`，`RST_REL` 之前），再用 `gap` 决定后续下拉落在 19 ms、59 ms、149 ms 还是更晚。

### 2.4.6 本卡的耐受地图已闭合：能活的都不翻转，会翻转的都活不下来

干净流程（`fast=1`，真毛刺；`revert=1`，每发自收尾；`u`+`w` 只在轮首一次）下，本卡 50 发的完整结果：

| 深压 | 可承受的重叠（`pw-40`） | 越过就死 | `DSOV=0` 出现过吗 | 判决数 |
|---|---|---|---|---|
| 337.5 mV（码 54） | 任意，含 `3×222 µs` / `gap` 到 4000 | 未观测到 | **从未** | ~40 |
| 331.25 mV（码 53） | ≤150 µs | 150~182 µs 之间开始概率性致死 | **从未** | 19 |
| 325 mV（码 52） | **0**（`pw=90`、重叠仅 50 µs 也当场死） | 立刻 | 从未 | 4 |

七个维度都扫过：`vd`、`pw`、`delay`、`gap`、`pulses`、`fast`、`revert`。全程 `CRC` 恒为 `0x55`、`DSOV` 恒为 `1`，连"跌太深"的 `CRC=0x00` 一次都没出现 —— 说明毛刺从未真正进入熔丝阵列的采样判决，只在 331/325 上把卡打死。

**两条由此确立的、与"参数没调对"无关的结论：**

1. **`fast` 决定毛刺是真是假。** `main.c:146-156` 的 `PROFILE` 换的是 VRM 的保护参数（`0x32: 0x7F81→0x0F81`、`0x30: 0xCE64→0xCE04` 等）。`fast=1` 时轨道真的被拉到目标电压（所以 331/325 会打死卡）；`fast=0` 保留出厂保护、轨道被钳住 —— 同一坐标 `334@54`，`fast=1` 下 4/4 死，`fast=0` 下安然 `under`。这就是"档案配方"里 `fast=0` 那一条在本卡上属于**空 dip** 的实测证据。
2. **`FUSECTRL=0x00000000` 是第三种状态**（既非 IDLE `0xe0040000`、也非 poison `0xBADFxxxx`）。它在 `331@pw=185` 上出现，随后卡仍在总线上但不敢再读。处置：**重启判决机**（POST 拉 `PERST#` → POR），重启后再读一次即回 `0xe0040000`，**不需要台架断电**。这使"每发代价"从一次手动断电降到一次约 1 分钟的主机重启。

**给后来者的判断**：本卡的 `DSOV` 位（`OPT_DISABLE_SW_OVERRIDE`）读 1，而任何能把轨道压到 331 mV 以下的动作都会在卡能读出判决之前把它打死。若继续在本卡上尝试，唯一还没被否掉的思路是"不等启动完成再读判决，而是在毛刺窗口内直接完成 `SENSE_CTRL`/`arm`"——那需要板子具备读 GPU 的能力（本卡的 SMBPBI 直读 `@P` 四次全无回显，板子读不到这颗 GPU），属于换架构而非换参数。

### 2.4.7 第三张卡（2026-11-24，同 SKU `10de:20c2`，同一波形）：同一深度上致死的是**脉冲数**

## 三、网格几何：`max ≥ ndelays × batch`

`main/campaign.c` 的 `point_budget_locked()` 给每个 delay 点 `max/ndelays` 次机会；电压 ladder 要在同一电压点攒够 `batch` 个判决才挪一格。

```
max=20, ndelays=6, batch=4 → 每点 3 次 < batch → ladder 不动 → 20 发全打在同一个 (delay=0, vd=300)
```

该浪费从判决流里看不出来（每条判决都合法）。`bench/crack.sh` 在开火前计算几何，不满足即拒绝启动。本卡使用 `max=12, ndelays=1, batch=2`；多点搜索时按公式放大 `max`。

## 四、跨轮台账

一个电源周期能买到的发数上限是"到第一次 poison 为止"，因此每轮发数必须累进同一张表：

```bash
bash $HOME/ga100vfi/bench/mkledger.sh    # 汇总所有 *-crack*/agent.log → logs/ledger.txt
```

判读表（`(delay, vd) → under/over/poison/lost`）：

| 表里看到 | 结论 | 下一轮 |
|---|---|---|
| 全 `under` | 还不够深 | `vd` 调低 |
| 全 `over`/`poison` | 太深 | `vd` 调高 |
| `under` 与 `over` 混现 | 边界在此 | 该 `vd` 附近加密 delay 点 |
| `lost` | 卡不在总线 | 该批发数不算数据，先按 §2.3 恢复 |

poison 那一发不由代理回传判决（红线所致），台账按板子记录的坐标补一条 `poison` 事件。

台账坐标必须包含波形几何。`(delay, vd)` 两个数不足以复现一发脉冲：`pw/pulses/gap/td` 每一项都改变物理结果。档案命中几何为 `3 × 222 µs`、`gap 150 µs`、`td=-40 vr=750 tr=-20`、`delay=54`；单发 `pw=15000`（15 ms @ 300 mV）按档案定义属 over（欠压横跨整个启动窗），实测两轮各一发 poison，已弃用。

### 4.1 判决链自身的排除实验

`bench/readtrip.sh` 一个脉冲不打，重放判决链的全部访问（含连写三次 `DSOV_SET=1`），`FUSECTRL` 全程 `0xE004…`。结论：判决链的读写不会把控制器打进 poison。

## 五、台架脚本

源文件在仓库 `bench/` 下，由 `tools/deploy_bench.py` 一条命令装到 `$HOME/ga100vfi/bench/`。部署会先清理旧文件再解包、规范化 CRLF、跑 `bash -n`、并在机器上实跑 `FUSECTRL` 四态归类。脚本清单与用途见 [../bench/README.md](../bench/README.md)。

`crack.sh` 开火前的六道闸门：

1. 固件版本闸门：`/api/status` 的 `net.build` 首词必须等于 `EXPECT_FW`（与 `main/board.h` 的 `GA_FW_VERSION` 同步，部署时断言），否则拒绝开火；
2. 速率闸门：`board.baud`（实际生效值，非请求值）必须等于 `EXPECT_BAUD`（默认 1 MHz）。波形配方是 1 MHz 的算术，总线自行降级后每一发的 dip 边沿都被拉长，与台账里的历史发数不可比；0.4.0 换了 I²C 引脚，接错线/无上拉/线过长第一个症状就是这里降级；
3. 等卡回 PCIe（只看配置空间，不碰 BAR0），必要时 `pci rescan`；
4. config-only 探活取真实 `vendor:device`（sysfs 缓存会说谎）+ 只读一次 `FUSECTRL` 判危险态；
5. 判锁态：`pwd=1` 放行；`pwd=0` 走 `@w 25 03` + `u` + 回读，仍 `pwd=0` 拒绝开火；
6. 网格几何 `max ≥ ndelays × batch`。

每道门各自对应一类无效发数：①整轮日志无法回答"哪版固件打的"；②整轮波形与档案不是同一个实验；③把"还没枚举"当卡死；④在 poison 态读 BAR0；⑤锁着开火整轮空转；⑥整轮塌在一个电压点。

烧写与冷启动复核各有一个入口：`bench/burn.sh`（试烧一条 → 独立重读逐行核对 → 续烧其余，每步真写前等人确认）与 `bench/postboot.sh`（先 `wake` 再谈生死：冷启动后 `Command=0x0000` 时 BAR0 整片读回 `0xffffffff`，与掉卡不可区分，判据是配置空间答不答 `10de:20c2`）。两者都是 2026-11-21 那次实烧的手工规程的直译，差别只在每一步现在由脚本执行。

### 6.3 五条事实

1. **`CMD_SENSE` 不刷新 option 影子寄存器。** `0x00820364`(`fbp`) 等只在 `PEX_RST`/devinit 重算；`SENSE` 只重解析熔丝宏自身影子（EFP/SBFE/CRC/DSOV）。验证记录是否被采纳必须 `PEX_RST`。映射本身不需要靠冷启证明：烧前影子等于链重放值（例 `(0x4290>>3)&0xFFF = 0x852`）。
2. **`EFP_STATUS(0x00820078)` 冷启后读 0，发一次 `CMD_SENSE` 才为 1。** ffcalc `burntool` 的 `in_write_window()` 要求 `EFP==1`，刚进窗口时会拒 burn；先 `sense` 即可。`ga100vfi.burn` 的 `window_ok()` 不含 EFP，`arm()` 之前先 `sense()`。
3. **`pcie_magic_gen4_dis` 即 `magic_d` 的 bit25**（`magic_d` 为 bit730 起 32 位，跨 block 45/46/47）。清该位必然使 `magic_d` 从 `0x16680000` 变 `0x14680000`。
4. **FF 链是追加/后写覆盖的。** 写错的记录可用新行纠正；本卡烧后剩余 174 行空闲。
5. **我们这条路径读不到 IFF 区（487..511）。** 与另一条独立采集（内核 `ffprobe` 的 `CMD_READ`）逐行对比：FF 区 0/265 行差异，IFF 区 20/25 行不一致，且任意行号偏移下均不吻合；该工具自身的多组采集在 IFF 区逐行相同。结论：IFF 区在本工具这条路径上读数不可信。`capture_rows` 默认区间已收至 `FF_ROW_MAX`。`replay()` 只使用 FF 区，此错误不产生显式失败。
