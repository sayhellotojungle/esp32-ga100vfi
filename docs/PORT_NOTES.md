# 架构与协议说明（0.3.1）

本文描述当前源码行为。引脚由 [board.h](../main/board.h) 定义，构建入口见 [BUILD.md](BUILD.md)。

## 硬件操作所有权

`main.c` 创建固定在 core 1、优先级 8 的执行任务。UART 和 HTTP 先提交完整命令，执行任务再按顺序处理。自动流程使用 `campaign_poll()` 协作式状态机，不另建一个任务同时操作总线。

队列以完整命令为单位，单条最多 255 字节，不包括 C 字符串终止符。超长、不完整、含 NUL 或内部换行的网页命令会被拒绝；UART 超长行会丢弃到行末，不会执行截断后的内容。队列满时返回错误，不静默丢掉半条命令。

自动流程运行时，手动硬件操作被拒绝；状态查询和流程停止仍可使用。停止请求会在当前同步操作结束后处理，不承诺中断一笔已进行中的 I²C 事务。停止或失败结束会尝试恢复控制器，`restore_ok` 报告恢复结果；成功结束不再额外复位或执行自动恢复。

OTA、网页 Wi-Fi 凭据写入和硬件执行共用维护锁。后台日志及状态快照另外同步，不允许读到新序号搭配旧结果字段。

## 时间与采样

复位仍由软件时间表执行。阻塞式 I²C、驱动调用和调度会造成迟到；移到单一任务并不消除这些误差。

- `slip` / `board.last.slip_us`：时间表步骤开始执行时的最大迟到量。
- `reset_slip` / `board.last.reset_slip_us`：实际复位释放操作的时间戳与计划零点的差。

有效总线速度在初始化与上拉检查后确定。状态中的 `requested_baud` 是请求值，`baud` 是用于设备配置和时间预算的有效值。理论事务时间只提供下限，不构成时序保证。时序限制详见 [CALIBRATION.md](CALIBRATION.md)。

## 串口兼容

原有单字符命令保留：`v u z w k K r j J b`。`g ...` 和 `@...` 是以 CR 或 LF 结束的行命令。主机客户端现在等待完整结束行，不会仅收到 `glitch done` 前缀就停止接收。

## 解锁序列与版本自证

`ensure_unlocked()` 的固定顺序：`CLEAR_FAULTS(0x03)` → 密码 `0xF2 0x7C 0x25` → `0x13=0` → `0x46=0x1229` → 回读 `0x46` 必须等于 `29 12`。先清故障是必需的：故障闩锁时控制器应答读、拒绝密码，而唯一能清故障的 `GA_CLR` 排在被密码门挡住的时间线内。`0x46=0x1229` 阻止 devinit 重新锁上 VRM，缺少它时第 1 发之后的每一发都在解锁门口返回。写不进 `0x46` 即返回 `config-id-0x1229-refused`。

`unlock_cmd()` 的失败分三类输出：`unreachable`、`password-refused`、`PARTIAL pwd=1 0x46-failed`。

版本号定义在 `main/board.h` 的 `GA_FW_VERSION`，启动横幅与 `/api/status` 的 `net.build` 共用；`GA_BUILD_STAMP` 为编译时刻，用于区分同版本号的不同构建。

常用状态与管理命令：

| 命令 | 当前行为 |
|---|---|
| `v` | 输出板卡状态 |
| `z` | 读取控制器状态 |
| `@W` | 查看网络状态；网页支持包含空格或特殊字符的独立 SSID/密码 |
| `@C status` / `@C` | 查看自动流程状态 |
| `@C stop` | 请求停止自动流程 |
| `@V <session> <attempt> <判决词>` | 经串口交判决（0.5.0），见下文「判决方通道」 |
| `@A [seq=N] [adopted=N] {json}` | 判决方心跳（0.5.0），回包带回页面留下的开跑请求 |

`@P`（SMBPBI 探针）与 `@O`（判决模式）随 0.4.1 一起删除：板载判决的通路在本台架从未答过，`@P` 因此没有可探的东西，`@O` 没有可選的模式。今天再发这两个命令会得到 `ERR unknown command`（它们落到 PMBus 命令解析器），这是诚实的答复而不是回归。

`@C start` 的选项仍使用 `key=value`。数值严格解析，未知字段、溢出和超出边界的配置会返回错误。`delay=` 列表使用独立解析状态，不再吞掉之后的选项。`max` 是总尝试上限；`max=0` 表示不限总次数，多点配置按点轮转。`mode=1` 仍被接受（旧命令行不必为此改写），`mode=0` 返回 `mode removed: the host judges every shot (mode=1)` —— 报错而不是忽略，因为要的是"请求方知道自己请了一个不会有人应答的判决方"。

原有完成行字段保留，并追加诊断字段：

```text
glitch done pwd=... e1=... writes_failed=... slip=... reset_slip=... diag_ok=...
```

遥测输出位于结束行之前。`diag_ok=0` 表示尝试后的诊断读取不完整；`writes_failed=0` 本身不能覆盖这类失败。准备或参数错误使用 `glitch ERR ...`，一般命令错误使用 `ERR ...`。

软件边界定义在 [glitch_plan.h](../main/glitch_plan.h)，用于防止非法参数、溢出和不完整计划，不是针对任意外部设备的电气安全保证。

## 自动流程与判决关联

每次启动创建新的非零 `session`；每次尝试递增 `attempt`。当前流程的模式固定，忙时启动失败不会偷偷修改模式。

关键状态字段：

| 字段 | 含义 |
|---|---|
| `running` / `phase` | 流程是否仍运行及当前阶段；恢复阶段仍保持 running |
| `session` / `attempt` | 当前会话和尝试编号 |
| `sequence` | 对应板卡完成记录的序号；尚未完成时为 0 |
| `awaiting_verdict` | 当前是否允许提交这一轮的外部结果 |
| `tries` / `valid` | 已发起尝试数 / 有可用分类结果数 |
| `nack` / `lost` / `timeouts` | 执行或通信失败 / 设备不可读 / 外部判决超时 |
| `restore_ok` | 结束恢复是否成功 |

外部结果必须同时携带 `session`、`attempt` 和 `r`。过期编号、未知结果或非等待阶段会被拒绝。对最近一次已接收的相同结果重试可获得确认，不会重复累计。结果提交的响应体为 `ok`；不匹配返回 HTTP 409。

主机代理保留未确认结果并重试网络提交，避免为重试再次执行会访问寄存器的分类。停止、重新启动或轮次变化后，旧结果被丢弃。

SMBPBI 判决路径（旧 `mode=0`）于 0.4.1 删除。它的帧格式始终属于未获目标卡确认的实现，而本台架对该端点的四次读全部无回执（[UNLOCK_AND_POISON.md](UNLOCK_AND_POISON.md) §一），因此这条通路既没被验证过、也不可用；留下的只有"每一发都被一条不存在的通路判成 LOST"这一种后果。判决词表（`goldilocks`/`hit`/`under`/`over`/`lost`）与 `main/oracle.h` 保留，它们是 `/api/verdict` 与 campaign 计数器的词汇，不再包含任何读硬件的代码。

## 判决方通道（0.5.0）

分工：能读 BAR0 的那一侧就是唯一有权开跑的那一侧。判决方（`host/ga100vfi_agent.py`）是人在需要时启动的进程，不是服务，所以板子与它之间不许有任何一方等另一方：判决方经串口推快照，页面经 HTTP 留开跑请求，各自在下次联系板子时读对方的格子。实现是 `main/peer.c` 里两块定长 RAM（快照 255 B、请求 191 B）加一把自旋锁——不落 flash、不排队、不分配，因此在毛刺飞行中不可能拖住执行器。

| 方向 | 形式 | 规则 |
|---|---|---|
| 判决方 → 板子 | `@V <session> <attempt> <判决词>` | 与 `/api/verdict` 同一套准入（同一个 `campaign_submit_verdict()`）。接受回 `verdict accepted …`，令牌过期回 `verdict stale: …`。五个判决词与 HTTP 完全一致：两条通路两套词汇，`lost` 就会在同一张台架上获得第二种含义。 |
| 判决方 → 板子 | `@A [seq=N] [adopted=N] {json}` | 快照必须是**单个 ASCII JSON 对象**、≤255 B；控制字段只放代码，中文由页面渲染。串口丢字节的结果是整块拒收（`peer ERR …`），而不是页面显示半截"健康"。`seq` 是判决方自己的计数，重发同一快照不会被当成新消息。 |
| 板子 → 判决方 | `peer stored seq=N req=none` 或 `peer stored seq=N req=<seq> <参数串>` | 心跳的回包就是"页面留了什么"，判决方不必再开第二条通道去问有没有人点了开始。 |
| 页面 → 板子 | `GET /api/req?op=start&…&seq=N` | 参数块**原样**交给判决方，板子不解析（板子若半解析一遍，就多一处会把参数弄错的地方）。字符集限于 `A-Za-z0-9_=&,.-`，因此不存在二次编码。已有战役在跑时返回 409：正在跑的一轮不是队列。 |
| 页面 → 板子 | `GET /api/req?op=cancel` | 撤回未被领取的请求；同时清掉"上一次的处理结果"，否则页面会继续播报一个刚被人不要的运行。 |
| 页面 ← 板子 | `/api/status` 的 `peer` 块 | `present`、`age_s`、`seq`、`req`（`none`/`pending`/`adopted`/`expired`）、`req_seq`、`req_age_s`、`info`（快照原样内嵌）。响应刻意不含请求体本身：这个响应是每个打开的页面每秒都要重读一次的东西，而台架上的 HTTP 服务只有一个 worker。 |

页面认识的快照字段：`state`（在做什么）、`gates`（发前闸门逐条结果）、`next`（下一发坐标）、`last`（最近一发的判决依据，含 `DSOV`/`CRC` 原值）、`ledger`（台账累计）、`halt`（停手原因码）、`note`（备注）。未知字段按 `字段名：值` 原样显示，所以判决方可以加字段而不必先改固件——固件不解释这些内容，只负责拒收形状不对的整块。

四条必须写死的规则：

1. **未被领取的请求 10 s 过期。** 判决方是按需启动的：如果"点了开始但当时没人听"会存下来，那么某天插上串口的那一刻就会自己开打一枪，而那时已经没有人盯着卡。请求要么当场被领取，要么作废。
2. **采纳声明优先于过期。** 判决方在 9.999 s 领取、回包在板子已判过期之后到达时，仍按"已采纳"呈现——运行确实起来了，说"过期"会藏掉一个真在跑的战役。
3. **无人判决即停战。** settle 之后等不到判决，`timeouts++` 之后战役以 `phase":"no-judge"` 结束（0.4.1 及更早是继续取下一个坐标）。既然人工判决不再是常规通路，沉默只有一个含义：判决方不在了；此时继续按 120 s 一发打下去，按常用 `max=60` 算最长是两小时的盲打，而坐标花掉就是花掉。
4. **串口命令整行分派（0.5.2），心跳每块 ≤100 B。** 单字符命令也要等换行才执行。0.5.1 及之前是"行首收到就执行"，而心跳载荷是一段 JSON：一行没能完整到达时，正文里的 `r`/`u`/`z`/`k` 就落在行首，于是一段本该只更新观测数据的快照自己动了硬件——本机实测一次 `PEX_RST` 脉冲外加每字节一行错误（当时 `PEX_RST` 线没接，动作落在空处）。判决方的每一行都以 `\n` 结束（`host/ga100vfi/glitch.py` 一向如此），所以这条只废掉"手敲一个字符不回车"这一种用法。
   串口没有流控，且**能吞下的速率远低于 115200 的线速**（本机 115200、CH340，判据为串口回包 `peer stored`）：

   | 发送方式 | 结果 |
   |---|---|
   | 单块 47 B / 71 B / 107 B | 10/10 完整 |
   | 单块 185 B | 1/10 |
   | 同一条 185 B 拆两块（92+93 B），间隔 5 ms | 3/10 |
   | 同一条 185 B 拆两块，间隔 40 ms | **9/10** |
   | 两条 90 B 连发（合计 180 B 一次突发） | 11/20 |

   三条对照排除了两个常见猜测：板子繁忙（每发期间并行拉 16 KB 的 `/api/log`）与安静时同样糟；把泵任务改成一次抽 512 B、空转睡 2 ms 也没有移动这道台阶。限制在 RX 路径本身（Arduino 核心的 `sdkconfig.h` 未定义 `CONFIG_ESP_CONSOLE_UART_RX_BUFFER_SIZE`）。所以发的一方按块控制：**一次 `write()` 不超过 100 B；更长的快照分块发，块间留 ≥40 ms**（硬上限仍是 255 B，`PEER_INFO_MAX`）。心跳丢一两次不改变战役状态机，靠 `peer.present` 与 `peer.age_s` 表达在线状态正是为此。

`@V` 与 `@A` 在处理"战役在跑就不许手工命令"这条规则**之前**被处理，且不取硬件锁：判决到来时战役正持有总线，而心跳必须能在毛刺中途应答——一个要等这一发打完才回的心跳，不能作为台架还活着的证据。

## HTTP 错误处理

`/api/cmd` 按 `content_len` 完整接收，再统一提交命令。过长请求返回 413；收包失败不执行已收到的前半段。错误连接不会在残留请求体未消费完时复用。

Wi-Fi 参数先 URL 解码，再按独立的 SSID 和密码验证、保存，避免空格分隔和百分号编码破坏凭据。NVS 擦除后的重新初始化及保存错误会被处理。OTA 检查镜像写入、结束验证和启动分区选择的返回值。

## 重启记录

运行记录放在 `RTC_NOINIT_ATTR` 区，带有效性标记。启动先读取上一轮记录，再清理本次状态。断电或无有效保留记录时不会伪造历史阶段。

50 ms 的 `esp_timer` 回调在时间表执行阶段监视心跳；心跳超时会释放复位线并请求重启。它不替代硬件测量，也不能保证 MCU 重启后外部电源控制器自动恢复。
