# 台架脚本（判决机上运行）

`bench/` 下的脚本承担开火、取证、恢复判据三类工作，运行在插着目标卡并跑 Linux 的判决机上。源文件随仓库走，不放在 `/tmp`：判决机每次重启清空 `/tmp`，脚本丢失曾两次把战役预检卡在"依赖文件不见了"。

## 部署

从 Windows 端（仓库根目录）：

```bat
set BENCH_HOST=<判决机IP>
set BENCH_USER=<判决机用户>
set BENCH_PW=<判决机口令>
python tools/deploy_bench.py
```

三个值都必须显式给出，仓库里不存判决机地址与口令；`BENCH_PREFIX` 可选，缺省为登录账户的 `$HOME/ga100vfi`。同理，所有台架脚本的板子地址都来自环境变量 `BOARD=http://<设备IP>`，缺 `BOARD` 直接退出 2——写死任何一台台架的地址，都会让下一个照做的人去打别人的卡。

部署步骤与断言（`tools/deploy_bench.py`）：

1. 打包 `host/` + `bench/` 上传解包到 `$HOME/ga100vfi/`；先删除旧 `bench/` 与 `host/__pycache__` 再解包，仓库里改名或删除的文件不会残留在机器上；
2. `tr -d '\r'` 规范化 CRLF，脚本加执行位，并为 `/tmp/.console.sh` 等旧路径留转发壳；
3. `bash -n` 检查全部脚本；
4. 断言红线判据在包里：`Poisoned` 与 `FUSECTRL` poison 判据、`STATE_UNKNOWN` 第三种态判据、判决行携带 `delay=`/`vd=` 坐标；
5. 在机器上 import 部署后的 `ga100vfi.classify`，逐一断言 `FUSECTRL` 四态归类正确，且 `classify()` 对 `0xBADF…` 与 `0x00000000` 都拒绝写 `DSOV_SET`。

第 4、5 步的意义：部署了没有防护的包比部署失败更危险。

## 开火

```bash
# 自变量只有一份出处：host/ga100vfi/shot_policy.py。先问它要这一批的配方，再交给 crack.sh：
(cd $HOME/ga100vfi/host && python3 -m ga100vfi.shot_policy --recipe)   # 例如 MODE=hunt 时给出
#   export MODE=hunt VD=363 MINV=344 MAXV=384 STEP=6 DELAYS=54 MAX=12 BATCH=1
#   export PREWARM_VD=368 WAIT=1500 FIRST_READ_DELAY=2 BAR0_SESSIONS=1 CONFIRM_READS=1
BOARD=http://<设备IP> $(上面的输出) bash $HOME/ga100vfi/bench/crack.sh
```

**不要在这里抄一份数值** —— 2026-11-26 之前这条命令行写着 `BATCH=2 VD=334 …`，而真实的搜索轴已经搬进
`shot_policy`（`MODE`/`SWEEP`/`HAMMER`）：文档里的旧值曾经让人以为"起点就是 334"，而 334 实测首发即死。

- **`MODE=hunt`（找区间）** = 粗阶梯 + 每发真读一次熔丝块（`BAR0_SESSIONS=1 CONFIRM_READS=1`）。config-only
  判决永远给不出 `over`，而没有 `over` 就画不出区间下沿。`MODE=hammer`（死磕一个坐标）才走零读
  （由 `HAMMER={BAR0_SESSIONS:0, CONFIRM_READS:0}` 显式导出 —— **全局默认是 2，不许改成 0**，否则人工直调
  代理就静默产出未盖章判决）。
- **`PREWARM_VD` ≠ `VD`**：预热发吸收的是【冷态第一发】这个危险状态，永远打在 `prewarm_vd_mv`（实测从没
  丢过卡的格子）；战役起点 `VD` 负责试深。两者混用的那天（11-26 08:54:22，`VD=363`）预热首发把卡打死，
  闸门按规矩拒开正式批 ⇒ 一个电源周期换回 **0 条判决**。
- **发后第一次读的时机 = `WAIT + FIRST_READ_DELAY`**（hunt：1500 ms + 2 s ≈ 3.5 s）。深格子是【在判决之前
  就死】的：实测卡在第 2 发后 +4~7 s 持续 off-bus，读排在 4+2=6 s 就每判不到。下限 3 s 是红线（不许排进
  卡自己的 PERST# 重枚举 / ROM 里读熔丝块）。

默认波形即档案命中几何：`3 × 222 µs`、`gap 150 µs`、`delay=54`、`td=-40 vr=750 tr=-20`。搜索几何（`VD/MINV/MAXV/STEP/BATCH/MAX/DELAYS`）可以调；波形几何只在 `under`/`over` 判据要求时改，并需留下比档案更强的证据。单发 `pw=15000` @ `vd=300` 按档案定义属 over（欠压横跨整个启动窗），已从默认值移除。

两个用发数换来的坑（`docs/UNLOCK_AND_POISON.md` §二.5 与 §十）：

- **`VD` 必须落在 `MINV..MAXV` 之内**，板子按 `require safe min_v <= vd <= max_v` 校验整个 campaign，而 `MAXV` 默认 **384** —— 只传 `VD=412` 会被整批拒掉（一发未耗，但预检要重跑）。固件的硬范围是 `GLITCH_MIN_MV..GLITCH_MAX_MV = 0..1000`：**380 不是硬件上限，只是 `campaign.c` 的默认上沿与档案约定**。
- **`PULSES` 与 `PW` 一样决定累计欠压能量，但它不进包络的族键**（族 = `pw × 相位档`）。第三轮在 `vd=380` 上 `3×222` 两发首发即锁死、`1×222` 两发全活且第二发命中：换 `PULSES` 等于换形状，而包络不会替你拦，族战绩表还会把两种形状算成同一个数。

台账目录名自描述（固件版本 + 波形几何 + 电压），因为跨轮复盘依赖目录名回答"哪版固件、什么波形、几发"。

### 判决机上实际执行的是哪几个文件（2026-11-26 核对，别再把批次归给错的脚本）

`temp/r_fast.sh` 最后一句是 `exec bash /root/mig-card2/run.sh`。那两层（`run.sh` → `batch.sh`）
**不在版本库里**，是历史手搓的；`batch.sh` 用 `setsid nohup env … bash bench/crack.sh` 起真正的批。
核对结论（原文存在 `temp/judge-entry/`）：它自己**不覆盖**波形几何（`VR=750 TR=-20 PULSES=2 PW GAP TD`
照抄调用方），`BATCH=1` 与 `ENVELOPE_GATE=0` 是它写死的，`PREWARM/CONFIRM_READS/STABLE_S/
FIRST_READ_DELAY` 走环境变量继承。之所以留下这两层：它们负责 presence 4 Hz 记录器、批进度轮询、
批末现场与 `DECISIONS.txt`。**风险也在这里**：这两层没有版本闸门，改了仓库不等于改了它们 —— 每批
开头 `板端时间表原文：pulses=2 pw=222 gap=150 delay=64 revert=0` 那一行是板端自己吐的，
认这一行比认脚本传的参数可靠。

### 健康区随机扫（`SWEEP=random`）

命中是概率事件，而"阶梯往深走一格"等于把每一发都押在悬崖上。所以开火几何可以不由人拍，改由包络
在**健康区**里随机生成：

```bash
BOARD=http://<设备IP> SWEEP=random NDELAYS=4 MAX=16 BATCH=1 PW=222 TD=-40 PULSES=2 \
  bash $HOME/ga100vfi/bench/crack.sh
```

（`DELAYS`/`VD`/`MINV`/`MAXV`/`STEP` 在这模式下会被包络给出的值覆盖，不用手填。）

`healthy_sweep()`（`host/ga100vfi/envelope.py`）随机的是三样：相位候选（从域里洗牌取，**冻掉的档
直接淘汰**）、电压窗口在 `HEALTHY_BOX` 里的落点与宽度、ladder 步长。三条约束：

1. 随机只发生在 `HEALTHY_BOX`（默认 `362..380`）内 —— 本台账里 poison 全在 354..358，而卡反复
   活着回来的地方在 366 以上；
2. **每个候选坐标都过 `check()`**：族冻结、按坐标禁火、rung 功课一条都不许绕。所以"打死过卡的
   那个点"不会因为换了随机窗口就被绕过去（`delay=64` 配不上任何盖住 362 的窗口）；
3. `pw` 与 `td` 不参与随机 —— 动那两根轴是换配方，不是抽签。

门禁因此也改了：`--delays` 会**逐个 delay 点都审**。以前只审 `delays=` 的第一个点，多点批次里后面
那些点等于没有门禁，而随机扫一批就是四个点。

预检拒绝开火的四种情况：

1. `FUSECTRL` 为 `0xBADF…` 或叫不出名字的值 → 绝不进判决链（poison 态读 BAR0 = 整机复位，事故 `logs/02`）；
2. `pwd=0` 且清故障后仍 `pwd=0` → 此时每发都在 `ensure_unlocked()` 门口返回，`PEX_RST` 不动，买到的是假 `under`；
3. `max < ndelays × batch` → 整个网格塌在一个电压点；
4. 等不到卡（`WAIT_CARD` 秒内配置空间不可达）→ 先按下面的顺序分清是哪一种。

## 卡不见了（按顺序，不许倒）

```bash
bash bench/card_probe.sh       # 设备是否还在、桥链路宽度、残留驱动
bash bench/link_retrain.sh     # 对桥发 Retrain + rescan（只写桥；本卡实测无效，见下）
```

```text
板子控制台（bench/console.sh 或 POST /api/cmd）：  @r 25 7e 1   # STATUS_CML，卡有没有电
```

判据（2026-11-21 重测，本卡 `10de:20c2`）：毛刺之后卡不在总线上时，**卡从不自愈** —— 同一发
命令零干预观察 60 s、240 次只读 `config` 全是 `0xffffffff`。

"不在总线上"有**两种**，处置与代价不同，别混成一条（混了就会对硬死反复摁 `PEX_RST`，白花时间）：

| 现象 | 救法 | 那一发的判决 | 算不算包络里的事故 |
|---|---|---|---|
| `config` 全 `1`，板子 `j`→`J` 后 ~0.3 s 重新枚举 | 板子自己就会做（每发的 `g` 自带 `PERST#`） | **作废**：`PEX_RST` 重放熔丝链，刚打出的 arm 一起冲掉 | 否，记 `void` |
| `config` 全 `1` 且 `PEX_RST` 叫不回；主机 `remove`+`rescan` 后 `01:00.0` 节点根本不出现、桥 `LnkSta` 停在 `0x1081`（`dllLA`=0） | 只能断电（`12V` + `3V3` ≥30 s） | 无从判决 | 是，记 `dead` |

今天（2026-11-21）第二种实测 6 次，其中 5 次是"拔电之后的**第一发**"。所以一次电源周期真正买
到的发数远比 `max` 少，发数稀缺这件事只能靠"每发都留下坐标与判决"来省。

`bash bench/revive.sh` 是把"先分清上表哪一行、再决定断不断电"这件事固化成脚本：卡不在场时先发一次板端
`k`（`PERST#` 拉低 100 ms 再放，就是一发里去掉坑的那个复位），等 `REVIVE_WAIT`（默认 6 s）让卡跑
ROM/devinit，再 `remove`+`rescan`，全程只碰配置空间、一次 BAR0 都不开、熔丝不碰。请回来退 0，
请不回来退 **4**（=该断电了，不是脚本失败）。两个硬前置：战役不在跑（正在打的时候拉复位会把
手里那发判决弄成假 `lost`），以及不在场才试。

2026-11-26 的实测形状：卡离链后串口 `z` 仍回 `cml=0x28 pwd=1 e1=0xc2ea`（**VRM 活着、没锁、E1 已被
卡自己的 devinit 交回 PWM-VID 模式**），但 `remove`+`rescan` 请不回来 —— 所以第二种态该走还要走，
只是现在先花 10 秒确认它，而不是直接断电。根源那篇（GA100VFI 原文）每次尝试都要重来一次电源周期，
那边成本 3 s（S3→S0），我们是一次人肉断电，所以这一步能捞回来的每一发都值得。

### 断电这一步怎么执行（2026-11-25 起，用户指令）

`bash bench/host-down.sh` —— 摘掉连打开关、把"这一批发生在什么状态上"记进台账、`sync`，然后
远程 `shutdown` 判决机；**判决机等人来通电，通电后由人告知判决方**。

为什么是关整台机器：卡的 `12V`/`3V3` 就是主机的供电，只有主机完全停转才等于"断电 ≥30 s"。
2026-11-25 试过不走主机的路子 —— 对 VRM 发 `OPERATIONS(0x13)` 远程断输出 —— 写全部被 NACK
（`I2C ERR no ack at any ladder rate`），落不了地。

### 不许在判决机上挂自动脚本（2026-11-25 事故之后）

2026-11-25 06:4x 判决机被自己冻死一次，凶手是"等卡时每 6 s 一次 `pci rescan`"的守卫循环：
打在已掉链的卡上，`rescan` 会把整机拖死（本 bench 早有一次同样记录，见 `link_retrain.sh` 那条
"实测 4/4 无效"旁边）。所以从现在起：

- **不开 `cron`、不开 `@reboot`、不留 `setsid nohup` 的连打循环**；一批 = 一次同步调用，跑完就停
- 卡掉链 → `bash bench/host-down.sh` 远程关机 → 等人通电并告知 → 再手动起下一批
- 等卡期间只读 `config`（只读是安全的：60 s 内 240 次实测无害），**不要**顺手 `rescan`

对上游桥下发 `Retrain Link` + `rescan` **实测 4/4 无效**：桥的 `LnkSta` 停在 `0x1081`、
`dllLA` 始终 0，EP 侧根本没重试训练。所以这一条只能当作"顺手排掉桥侧故障"的便宜判据，不要
指望它把卡救回来；`link_retrain.sh` 保留是因为它顺带回答"卡有没有电"。

代价要说清楚：`PEX_RST` 会**重放熔丝链**，所以靠它救回来的那一发读不到有效判决（刚打出来的
arm 一起被冲掉）。掉链的发＝白烧一发，降白烧率只能靠坐标与节奏，不能靠恢复手段。

`FUSECTRL` 是 poison（`0xBADFxxxx`）而设备仍在：先让板子把 `PEX_RST` 按住 2 s（实测足够，
`0xbadf510e → 0xe0040000`，`device id` 也从 `10de:2080` 回到 `10de:20c2`）；仍不清才重启判决机
（POST 拉同一根线），最后才断电。毒态在 `config` 的 `device id` 里就看得见，一次 BAR0 都不用开。

### 板子自己重启了（`board.boot` 涨了）

`/api/status` 的 `board.reset` 里出现 `WATCHDOG ... step=11 act=8` 就是这一类：板载毛刺看门狗在
时间表的**最后一笔写**（毛刺之后恢复 `VOUT_MIN`）上咬了。成因不是写失败，是写太久 —— 卡正试图
脱离复位的那一刻 MP2888B 会拉伸时钟，而 `scl_wait_us` 是**每根时钟线**的容忍上限，20 ms 的传输
超时又只在事务边界检查，于是一笔 16 位写能拖过 250 ms。看门狗照章 `esp_restart()`，而**战役状态
在板载 RAM 里**：剩下没打的发数一起蒸发。2026-11-25 上午一个电源周期内 `board.boot` 就涨到 3，
`MAX=60` 的两批分别停在 13 发与 17 发 —— 一批跑不完、`phase` 突然变 `idle` 且 `tries` 归零时，
先看 `board.boot`：涨了就是被咬，不是跑完，也不是掉卡。

0.5.3 起：时间表所用设备的拉伸容忍压到 2 ms（同一条总线实测最坏单步 95 µs，20 倍余量），时间
序列期间总线若已掉线就直接判那一写失败、不再走波特率阶梯（那是唯一一条可能长过 250 ms 的路径）。
留痕也修了：`phase` 改取看门狗自己写下的 `bite_phase`，并新增 `stale=<us>` 报出真实的阻塞长度
（旧留痕一律是 `phase=2`，那是 `esp_restart` 落地前被应用核改写的值，而 `PH_GLITCH_PREP` 这个相位
看门狗根本不开火 —— 一个自相矛盾的现场让我们把两轮排查送错了方向）。

### 自变量必须写在脚本本体里，不能靠调用方的环境

远程开火走 `ssh root@… bash -s < 本地脚本`，所以**本地设的环境变量不会跟到判决机**（本地 PowerShell 里
`$env:PW=800` 或 `PW=800 python …` 两种写法各坑过一次：前者根本没执行，后者远端吃的是默认值，结果记成
`pw=800` 的那一批实际打的是 `pw=222`）。规则：一批的自变量（`PW`/`TD`/`VD`/`DELAYS`/`MAX`/`SWIN`/`REVERT`）
用 `export` 写进被上传的那个脚本本体，脚本自报表头再把它用的值打一遍 —— **台账里写的形状必须是板端真的
打过的形状**，这类错误只有在事后复盘时才发现，而那时发数已经花掉了。

## 台账：哪些发算打过、哪些算事故

包络门禁（`host/ga100vfi/envelope.py`）按族（`pw` × 相位档）统计事故，冻结反复打死卡的形状。
所以**每一行台账的含义都是判据的一部分**，四类必须分清：

| 判决 | 含义 | 算打过 | 算事故 |
|---|---|---|---|
| `under` / `over` / `hit` / `goldilocks` | 判决读回来了 | 是 | 否 |
| `poison` / `dead` | 卡被这个形状打进毒态，或端点自己关掉、只能断电 | 是 | **是**（`FATAL_CLASS`） |
| `lost` | 判决没读回来，卡还在 | 是 | 否 |
| `void` | 判决作废：桥 retrain 失败，板子拉 `PEX_RST` 就把卡叫回来了 | 是 | 否 |
| `nojudge` | 板子打了、判决 0 行，但卡仍应答 `config` | 是 | 否 |

三条踩过的坑：

1. `lost` **既不是事故也不算反应**。本台账 44 发 `lost` 的深度从 `vd=339` 铺到 `vd=380`，与深度
   无关，是链路/台架现象。上一版把它算进"over 类"，结果把唯一零硬史的族（`pw=222`）冻掉了 ——
   方向正好反了。它只进"链路健康"那一行。
2. **判决作废不能记成 `dead`**。台架自己恢复得动的事件如果被记成事故，门禁就会拒绝一个其实零
   硬史的族：`pw=222` 曾被这种行凭空扣上 5 发事故，而它是本卡唯一零硬史的宽度。
3. **板子打了但判决 0 行的那一发必须进台账**（`crack.sh` 收尾时按现场证据补 `dead`/`nojudge`）。
   以前这种发根本不留痕，于是"刚把卡打死的那一族"在包络里依然显示零事故，下一轮门禁照样放行
   同一个形状去打死第二次。判决词也**不列白名单**：写的一方加新词，读的一方若列清单就静默丢掉。

同一 `attempt` 的重复行（判决 409 后代理会重试，`agent.log` 与 `ladder.log` 各一份）只算一发，
否则"浅档已攒够 12 发"会变成假话。

## 节奏：命中是概率事件

不存在"确定的临界值"，也不存在"打了很多发零反应所以这个形状不行"这种判据 —— 零反应只是还没
命中。到了包络边缘应当**在同一族上连续补发**，而不是换形状重开一局。配方每张卡都可能不一样：
台账里的数字是本台架本张卡的战绩，不是定律，不要抄成别人的起点。

## 固件版本自证

版本号定义在 `main/board.h` 的 `GA_FW_VERSION`，启动横幅与 `/api/status` 的 `net.build` 共用该宏；`GA_BUILD_STAMP` 记录编译时刻，用于区分同版本号的多次构建。

三处断言构成链条：

1. `tools/deploy_bench.py` 部署前断言 `main/board.h`、`bench/crack.sh` 的 `EXPECT_FW` 默认值、`host/pyproject.toml` 三处版本一致，并断言部署包含 `EXPECT_FW` 闸门；
2. `ota.sh` 要求镜像 sha 前缀等于 `EXPECT`，刷完回读 `net.build`，字段缺失即退出 4（用法 `BOARD=http://<设备IP> IMG=… EXPECT=<sha前缀> bash bench/ota.sh`）；
3. `crack.sh` 开火前要求 `net.build` 首词等于 `EXPECT_FW`（当前 `0.5.9`），不等即退出 3。

`bench/crack.sh` 的日志目录名取 `build` 首词，因此跨轮台账能回答"这一轮是哪版固件"。绕过闸门（`EXPECT_FW=any`）的代价是这轮日志不可追溯。

`crack.sh` 还有一道**速率闸门**：要求 `/api/status` 的 `board.baud`（实际生效值，不是请求值）等于 `EXPECT_BAUD`（默认 `1000000`），不等即退出 3。波形配方是 1 MHz 的算术（一笔 16 位 PMBus 写 36 µs，档案的 `delay` 就是对着这个宽度标的），总线自己降级到 400/100 kHz 之后每一发的 dip 边沿都被拉长，打出来的判决与台账里前面那些发不是同一个实验。0.4.0 换了 I²C 引脚，这条从"有用"升级成"必查"：接错线、忘接上拉、线太长，第一个症状都是这里降级。降级速率下强行开火用 `EXPECT_BAUD=any`，并在台账里另记实际速率。

开火的两个物理开关（0.5.4 起）：`SWIN=<us>` 让每一发在毛刺期间用 `0x8b` 采真实轨压（进 `board.log`
的 `vs` 行），`REVERT=1` 把 VRM 恢复挪进时间表（`post+500 ms` 那笔 `GA_MODE`）。两者默认 0，即档案里
那 190 多发的形状。**为什么值得开**：0x8b 是本台架唯一的物理反馈，而 2026-11-25 第一次打开就把方向
改写了 —— 命令里 372 mV 的坑，轨上实测只掉 70 mV（脉冲期间）/ 140 mV（脉冲之后 ~1 ms），也就是
`vd` 在 300..380 之间扫动的几乎只是寄存器值；同一发的坑前基线读回 753 mV，与配方里 `vr=750` 的恢复
目标对得上，所以这个读法本身是可信的。代价要知道：`SWIN` 自己会往时间表里塞 7 笔 ~90 µs 的读，实测
把 `PERST#` 的释放推后 ~300 µs —— **采样批不是原配方的复刻**，它是测量，判决不能拿去否证坐标。
`0x8b` 是 VRM 内部滤波后的值，一个极窄的深坑可能被报浅，这条留给更密的采样网格。

轨道实测还指出一条**不需要改固件就能走的新轴**：`delay` 只能非负，但 `td` 可正 —— `TD=+800 DELAYS=0` 会让脉冲落在
`GA_RST_REL`（计划时刻 0）**之后** 800 µs，即先放卡出复位、趁它自己启动的浪涌把轨往下拽的时候再补一脚。今天四次实测
的下探最低点（611~624 mV）恰好出现在释放之后 ~0.4~1 ms，所以这一侧才是"对着坑底打"的位置，而档案 190+ 发的 `td`
全是负的（`td=-40`），这一侧从没打过。

**地址不是身份。** 下面那条 11-23 的板端实测写的是 `192.168.67.117`，而 2026-11-26 开火的这块板（一直在环、
接 47/48 与 `PEX_RST` 的那块）DHCP 租约正好也落到 `.117`，`.118` 反而不再应答 —— 两个时期的同一地址是两块
不同的板。所以开火前认板只认三样：`net.build` 的**编译戳**（要与 `firmware/RELEASE.json` 那次构建一致）、
镜像 **sha256**（`bench/ota.sh` 自证过的那串）、以及打完一发之后 `board.last` 的 `wfail=0 / diag_ok=true /
sw=0xf302`（证明 47/48 上真有一颗 MP2888B 在收写）。第三条是唯一能区分"板在但没接线"的证据，`/api/cmd` 的
`z` 只回 `queued`，控制台不通时它读不出来 —— 这时用 `MAX=1` 打一发探针比信地址可靠。

## 0.5.5：坐标是码、判决要盖章、每电源周期第一发是预热

评审另一 AI 的《命中准确度与流程》之后落地的四条（概率模型与依据见
`docs/UNLOCK_AND_POISON.md` §二，这里只写操作上要知道的东西）。

**1) 坐标的真实单位是 PMBus 码，不是 mV。** `VOUT_COMMAND` 的 LSB 是 6.25 mV
（`main/glitch_plan.c` 的 `mv_to_code`）：`366/368/370` 是同一个码 59，`372/374/376/378` 是同一个码
60。11-21 那次命中的"372→370→368→366 阶梯"其实只有两个坐标，而 300..380 这段合法带只有 **14 个
坐标** —— 我们两天打了 ~230 发。0.5.5 起：战役梯子按码步进、**不重复发本档已判过的码**，码打满就
`phase=exhausted`（这是结果，不是故障）；`/api/status` 的 campaign 段多 `v_code` 与 `codes_tried`，
判决行多 `code=`。**锤击模式豁免去重**：`VD=MINV=MAXV` 就是有意重复同一码，此时永远不会
`exhausted`。台账从此要带码：`vd=372(code60=375mV)`。

**2) `lost` 不再把梯子往浅处推。** 旧 `campaign.c` 把 lost 记成 `over`，卡离开 PCIe 之后每一发都
被当成"坑太深"，于是剩余发全打在一张看不见的卡上（11-20 实测：三个 lost 轮各 `tries=2`，其中一发
谁也没判过）。现在 lost 单独计数，不动梯子，同一档两次或连续三次直接 `phase=lost` 收摊；代理侧
`--max-lost` 那道刹车照旧保留。看到这两个 phase 都是"该停下来看现场"，不是"再补一发"。

**3) 判决要盖章（新旋钮 `CONFIRM_READS` / `STABLE_S`）。** 11-25 那 40 发约 1/3 把 CRC 读成
`0x57/0x75`（基线 `0x55`）：单发单读时"我们读早了"与"卡真的动了"同形，而判决词却是终局的。现在
**非基线**读数必须连读两次（间隔 `STABLE_S`，默认 1 s）才盖章；两次不一致时取更报警的那一份，判决行
标 `stable=NO`。三条绝不追加 BAR0 会话的硬规矩（lost / 熔丝块没读到 / 健康基线）写在
`_needs_confirm()` 的注释里 —— 那是 11-20 一发 lost 里开过 15 次 BAR0 换来的。**读 `stable=NO`
的那一行既不能当反应、也不能当没反应**；命中只认 `burn status` 的 `window: OPEN`。

**4) 每电源周期第一发是预热，不是数据（`PREWARM=1`，默认开）。** 三次"批内首发打死卡"里两次是拔电
后的第一发，11-21 的记录同样是 6 次掉链里 5 次发生在拔电后第一发。`crack.sh` 现在在正式批之前先打
一发**逐参数相同**的预热发（含 `wait=$WAIT` —— 预热的是"这张卡的第一发"这个状态，任何一项不同就变成
在预热另一个实验），由一个**独立代理**判决，写进 `$DIR/agent-prewarm.log`，正式批的 `agent.log` 与坐标
清点因此仍然干净。预热发的判决是开正式批的**闸门**：只有 `under` 才继续；`goldilocks`/`hit` 就立刻停手
去 `bench/window.sh`，`over` 按 poison 处理，`lost` 先断电，**没有任何判决行**（板子没打出去）同样不许
继续。这一发打的就是本批坐标，"没人判就当它没发生、接着打 60 发"万一把它判丢了，就是我们一直在骂的
"用假 under 换真反应"，而且这次换掉的可能是唯一一次命中。卡回不来时**这里绝不按 PEX_RST**（万一那一发
就是命中，按一下就是把熔丝链重放一遍，那颗 arm 只有一个）。要回到旧行为用 `PREWARM=0`。

**5) 每批自动出两张表（`bench/timeline.sh`）。** 固件从 0.3.x 就在免费记每笔计划步
`st act/want/got/dur` 与每发 `slip/reset_slip`，而我们一次都没按 act 分组统计过 —— 于是"A 类时刻不
确定"被引用了十几次，没人知道抖的是哪一步。`crack.sh` 批末自动跑 `python3 -m ga100vfi.timeline
"$DIR"`：按 act 的到达偏差/总线阻塞分布 + reset_slip 分布 + 0x8b 轨压最低点及其相对释放沿的时刻，
再按**码**清点这一批真正覆盖了几个坐标、脏读比例、以及 `config 应答 / 第一次开 BAR0` 的时刻分布。
规矩：**引用"A 类时刻不确定"或"我们扫过这一带"之前，先给出这两张表**。代理判决行的 `t_cfg=/t_bar0=`
就是为后者记的，但这两列**不许读成"卡的静默有多久"**：`t_cfg` 只回答"卡答话有多快"，而卡再没答话的
那些发压根不在这个分布里（表自己会喊"这是幸存者分布"）；`t_bar0` 的下界就是我们定的
`FIRST_READ_DELAY`。所以"下限还能不能调小"只能由**没答话的那些发**回答，胆量和幸存者分布都不算。
在攒够几十发之前，下限保持 4 s 不动。

**6) 一个必须记住的坑：`op=start` 就是开火，"我以为卡侧断电"不是安全前提。** 0.5.5 上板自证时我以为
判决机还关着，于是让 `fw055_selfproof.sh` 走到了 `op=start`，板子回 `tries=1 / awaiting_verdict /
writes_failed=0` —— 事后用 `uptime` 一比：机器那时已经开机 18 分钟，卡是在线、带电、被打的。所以这条
不是"poweroff 切不断 VRM"（我没证明过这件事），而是：**任何 `op=start` 之前必须自己现查三件事** ——
判决机 `uptime`、卡 `config[0..3]`、有没有代理在线准备判决。缺任何一件，这一发就是无人认账的一发。
自证脚本现在要求 `ALLOW_SHOT=1` 才许走到 `op=start`，且开火前后各读一次 config（`temp/fw055_selfproof.sh`）。

## 0.5.6 / 0.5.7：让"现在有没有人判决"第一次成为可观测的事

触发这两版的是操作员看着 WIFI 页面问的一句"这提示有误吧"。`crack.sh` 的代理明明在判每一发，页面的
"判决方"那一格却显示"未运行"，而且那句话写的是"经串口连本板" —— 两个错：通道是 WiFi/HTTP（串口是
**人**的逃生舱 `bench/console.sh`），"未运行"更是把"板子没收到心跳"当成"没人判决"这个事实陈述。板子
那侧 `@A` 从 0.5.0 就实现好了（`main/peer.c` + `main.c:peer_cmd`），缺的只是主机侧从来没发过。

**1) 代理真的发心跳了（`@A`）。** 启动即发一份，之后 1 Hz 续期（过期门是固件的
`peer.h:PEER_STALE_US`=5 s，只有一份，页面不再自己抄一个 5），每条停手路径
（`presence`/`poison`/`fusectrl3`/`lost`/`reacted`/`keyboard`）额外 `force` 一份 —— 页面里一直空着的
`last`/`ledger`/`halt` 三格第一次有真内容：代理**为什么**停手在批中就看得见，不必等批末翻
`agent.log`。

**2) 载荷必须是整包可打印 ASCII 且 ≤ 240 B。** `peer.c` 的 `ascii_json_object` 逐字节查 0x20..0x7e，
混进一个中文就**整包被拒**，于是页面又被*静默地*变回"未运行"。所以主机侧先消毒（剔非 ASCII、超预算按
`note→gates→next→ledger→last` 丢字段，`state`/`halt` 最后才动）。

**3) 心跳失败绝不影响判决。** 只记 `peer_ok/peer_err`，第一份心跳成功与否都打印在 `agent.log` 开头 ——
页面说没判决方时，这一行是分清"代理没起 / 起了但板子不收 / 板子收了但过期"的第一手证据。
`--no-peer-heartbeat` 只给调试用。波形在跑（`phase=executing/settle`）时尽量不发，但超过半个过期周期
（2.5 s）照发：本台架量过"观测本身就是扰动"（0x8b 那 7 笔把 `reset_slip` 从 8~231 µs 推到 370 µs），
可观测性也不能贵到让页面撒谎。

**4) 回包里若带页面上递交的 `op=start`，只打印不执行。** 代管开火＝绕过 `crack.sh` 的发前闸门（poison
预检、锁状态、固件版本闸门）。开火方始终是 `crack.sh`。

**5) 0.5.6 自己漏掉的那一半，是它的上板自证抓出来的（这条值得单独记）。** 刷完 0.5.6 我照例起一次只读
代理看 `peer`：present 从 false 变 true、seq 在涨、info 带 halt —— 对的一半成了。然后把代理杀掉，6 s
之后板子仍回 `{"present":true,"age_s":6}`。`present` 在 `peer.c` 里是"本次开机以来收到过快照"的**闩锁**
（`peer_store` 置位，只有 `peer_init` 清），过期只改 `age_s` 这个数；于是 0.5.6 那三态文案按 `present`
分支必然走错：判决方早就不在了，页面说"在线"。**这比原来的"未运行"更毒** —— 那句只是不精确，这句是
反话，而且它同时让**开火按钮保持可用**。0.5.7 把闸门做成算出来的（`PEER_STALE_US`），快照本身
（`seq`/`info`）仍闩锁保留，因为代理死了之后它留下的 `halt` 是唯一的现场说明。最该反省的是：
`test_peer.c` 的文件头**早就写着**"a heartbeat that goes stale"是这里最值得测的规则，却从没人实现它、
也从没人断言它 —— 57→74 条断言补上的正是这个空位。**"注释里承诺过的规则"必须有一条断言配着，否则它
只是句愿望。**（0.5.6 那块镜像 sha16 `e3da2efe8e86fd01`，只存活了一小时，判决机上还留着
`/root/esp32-ga100vfi-0.5.6-app.bin`；本地 `temp/esp32-ga100vfi-0.5.6-app.bin` 是同字节副本。）

**6) 两个顺手钉住的坑（都是这次加心跳时踩到的）。**

- `run_forever(agent, poll=0.0, …)` 曾经让 **presence 看门狗一次都不跑**：看门狗在内圈 `while monotonic() < now+poll` 里，`poll=0` 时内圈直接跳过，于是"卡已离开总线也照样把整批发完"这唯一一层保护静默消失，循环还永久空转（我自己的测试就是这么挂住的）。现在 `poll` 被抬到 0.05 s 下限，并有 `test_poll_zero_cannot_silence_the_presence_watchdog` 钉住。**任何保护逻辑都不许住在"只有采样周期非零才执行"的分支里。**
- 仓库里的 UTF-8 文件**不许用 PowerShell 的 `Get-Content -Raw` + `Set-Content -Encoding UTF8` 原地改写**：Windows PowerShell 5.1 的 `-Raw` 在未显式 `-Encoding` 时按 ANSI(GBK) 读，中文注释先解码成乱码再按 UTF-8 写回，整份脚本就毁了（本次是 `bench/crack.sh`，`bash -n` 当场在第 81 行报语法错）。恢复走判决机上最后一次部署的副本（`temp/get_bench.py`，sftp 取字节再覆盖，解码失败就抛错绝不写坏文件）。改文件用 edit 工具，或在 WSL 里 `sed`。

## 0.5.8 / 0.5.9：归因表第一次反过来否掉了我们自己的结论

`bench/timeline.sh` 的 timing 表今天（11-26）第一次被用来指方向，结果分两步：

1. **0.5.8（抬执行器优先级 + 近端禁调度自旋）**：动机是 `GA_RST_REL` 到达偏差 p50=118 µs /
   max=219 µs，而板上自己的 esp_timer 心跳回调（prio 22，同绑 core 1）每 50 ms 一刀，看着正好是
   这个量级的嫌疑人。**A/B 结果：没塌**（0.5.8 第一发实测 +132 µs）。优先级仍然该抬（那是免费的
   确定性），但它治的不是这一样病。
2. **0.5.9（重锚 `GA_REANCHOR`）**：真机制在逐 act 原文里 —— 坑的第一笔 VOUT 写实测 `dur` 是
   114/211/223/309 µs（计划 36 µs，卡在被拉住复位时拉伸 SCL），写结束于 +114/+212/+127，释放沿
   落在 +118/+219/+132：**释放沿只是排在那笔阻塞写后面**，与调度器无关。真正被搞坏的是几何：
   "坑开始"跟着这份迟到漂，而"坑结束"仍钉在 `+pw` 上，于是**坑的实际长度随机在 108~202 µs**
   （配方写的是 222 µs）。所谓"同一发打了 60 次"，物理上是 60 个不同长度的坑。
   现在坑的第一笔写被标成 `GA_ANCHOR`，它落地后后面每一步整体平移同样的量：`pw/gap/td` 这些相对
   关系一个字不改，但第一次真的执行。卡侧那份迟到换个名字继续记：`glitch done … stretch_us=N
   reanchor=1`，`/api/status` 的 `reanchor` 与 `exec_prio`（读回来的实际值）让台账能证明每一发跑在
   哪种模式下。`-DGA_REANCHOR=0` / `-DGA_EXEC_PRIO=8` / `-DGA_CRIT_SPIN_US=0` 各自可退回旧行为。

一句话教训：**"释放沿抖 200 µs"这张表一直是真的，错的是我们把它读成"我们的调度抖"**。以后先看
`dur` 再看 `got-want`：偏差等于前一笔写的 `dur` 时，那是排队，不是抢占。

板端实测沿革（**引用这一格之前先看日期，别把旧的当现场**）：2026-11-23 那格记录的是 `192.168.67.117` 跑 `0.5.2`、`boot = 3`、RSSI −46，接线状态"本板只接本机 USB 串口与网线，`I2C`（47/48）与 `PEX_RST` 均未接，卡不在环" —— 所以那一轮的真机自证只覆盖固件自己能保证的部分，见 [CHANGELOG](../CHANGELOG.zh-CN.md) 的 0.5.2 一节。2026-11-26 起本板**在环**（`I2C` 47/48 与 `PEX_RST` 均已接；卡为 `10de:20c2` / 64 GiB / 8-of-12-FBP，`fbp_defective=0x2d`），现在跑 `0.5.9`（stamp `Nov 26 2026 12:01:23`，app bin sha16 `09b2d4a9575183a7`）；`0.5.5`（stamp `Nov 26 2026 10:40:02`）打完过今天 02:51 与 02:58 那两批 60+60 发，`0.5.8` 打完过 03:52 那批的 2 发（预热发判 `under` 后卡掉链，正式批第 2 发打在已掉链的卡上，presence 看门狗停战），`board.baud = 1000000`（这是 I²C 时钟，不是控制台波特）。来路记全：先是 OTA 到 `0.5.0` 失败（那块镜像每次启动都在开 HTTP 之前 abort，handler 表 8 条装不下 9 条路由），板子停在启动循环里、HTTP 不可达；然后人工 `BOOT`+复位进下载模式，用 `esptool` 把 `0.5.1` 的 app 同时写进 `0x10000` 与 `0x310000`（这块板的 otadata 两条 seq 记录都过不了校验，判不出引导槽，两个槽写同一份就不必判），`nvs` 未动所以配网信息还在；`0.5.2` 走的是常规 OTA，写的是非活动槽。因此：**两个槽都是 0.5.x，板上的 `0.3.2` 退路已不在**（镜像在 git 里）；这块板的 CH340 既不能靠 DTR/RTS 自动进下载模式，`esptool` 的 RTS 硬复位也传不到 `EN`，所以刷完必须人工上电。0.5.x 把 I²C 默认引脚定在本台架实际接线 47/48，**不需要移线**。0.3.1/0.3.2/0.4.x 的镜像记录见 [CHANGELOG](../CHANGELOG.zh-CN.md) 与 `firmware/RELEASE.json`。
